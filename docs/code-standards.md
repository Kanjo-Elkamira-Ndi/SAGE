# SAGE — Code Standards

## General
- TypeScript everywhere, `strict: true` in both apps. No `any` unless justified with a comment.
- No ORM. Raw SQL via `pg`, always parameterized (`$1, $2, ...`) — **never** string-concatenate user input into a query.
- Prefer explicit over clever. This project has a supervisor/client reviewing it — readable code matters as much as working code.
- One export style per file where possible (named exports preferred over default, except for React page components and the Express app itself).

## Naming
- Files: `kebab-case.ts` for backend, `PascalCase.tsx` for React components, `camelCase.ts` for hooks/utils.
- DB tables/columns: `snake_case`. TypeScript objects: `camelCase`. Mapping happens at the query-result boundary (a small `mapRowToX` function per entity), not scattered through business logic.
- Booleans read as questions: `isActive`, `hasSubmitted`, `canEdit`.
- Route handler functions named by action: `createCourse`, `listMaterials`, `gradeSubmission` — not `handleCourse` or `doStuff`.

## Backend Conventions
- **Routes → Controller → Service → Query** layering, strictly. Controllers never contain SQL. Services never touch `req`/`res`.
- Every route validates its input with a Zod schema before the controller logic runs (via a shared `validate(schema)` middleware).
- Every route explicitly declares required role(s) via `requireRole(...)` middleware — no relying on "the frontend won't show this button."
- Errors are thrown as typed `AppError(code, message, httpStatus)` instances, caught once in a central error-handling middleware. No ad-hoc `res.status(500).send(...)` scattered around.
- All SQL lives in `db/queries/<entity>.ts` as named functions (`findCourseById`, `insertMaterial`, ...) — never inline raw SQL strings inside a service function body; the query layer is the only place that touches `pg` directly.
- Async/await throughout, no unhandled promise rejections — wrap route handlers in a small `asyncHandler` utility.

## Frontend Conventions
- Function components only, hooks-based.
- Data fetching via **TanStack Query** — no ad-hoc `useEffect` + `useState` fetch patterns. Each feature exposes typed hooks (`useCourses()`, `useCreateAssignment()`) built on top of `apiClient`.
- Forms via **React Hook Form + Zod** resolver — validation schemas shared in spirit (not necessarily in code) with backend schemas.
- Styling: Tailwind utility classes; component variants via `class-variance-authority` where a component has multiple visual states (see `ui-context.md`). No inline `style={{}}` except for truly dynamic values (e.g. chart-driven colors).
- Component size discipline: if a component file exceeds ~200 lines, look for a natural extraction (sub-component, hook) before continuing to add to it.
- No prop-drilling more than 2 levels — use context or colocate state closer to where it's needed.

## Git & Commits
- Conventional commits: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`.
- Branch naming: `feature/<module>-<short-desc>`, e.g. `feature/quizzes-ai-generation`.
- No direct commits to `main` — even solo, use PRs against a `develop` branch for anything non-trivial; it creates a natural review checkpoint and a clean history for the capstone writeup.

## AI-Generated Code (opencode/Lovable/etc.)
- Any code generated by an AI agent must be reviewed against this file and `file-structure.md` before being accepted — agents will default to their own conventions unless explicitly pointed at these docs.
- Agents must not introduce a new ORM, a new state-management library, or a new folder pattern without it being a deliberate, reviewed decision.
- AI-generated SQL must be parameterized and reviewed for injection risk exactly as if a human wrote it — no special trust extended.

## Testing (lightweight, given solo timeline)
- Backend: unit tests for pure logic (risk scoring, GPA calculation, grading) are non-negotiable — these are the parts a client/supervisor might scrutinize.
- Backend: integration tests for auth flow and at least one full CRUD module as a template others can follow.
- Frontend: component tests optional for v1 given timeline, but critical flows (login, submission upload, quiz submit) should have at least a manual test checklist maintained in `workflows.md`.
